## Stage 3 — Database + Migrations + RLS + RBAC (✅ complete, same session)

User confirmed the database name: `real-estate` (not the old CRM's `real-state`). Scaffolded a
fresh `REAK.Api` (.NET 10 Web API + EF Core 10 + SQL Server) at the repo root.

Built the full 57-entity schema across every table group the spec calls for — identity/tenancy,
Nepal location hierarchy + land area units + property/purpose/amenity/currency reference data,
the listing/demand mirrored structure with isolated contact tables, the matching engine,
collaboration workspace + contact disclosure, notifications, feature flags, append-only audit
log, and CMS content types. All-`Guid` primary keys per spec §21. Applied via two EF Core
migrations (`InitialCreate`, `AddRowLevelSecurity`).

Implemented RLS as **native SQL Server row-level security** (not just app-level filtering) —
predicate functions + `CREATE SECURITY POLICY` in a `Security` schema, covering listings,
demands, both contact tables, the collaboration workspace + all 8 child tables, plus an
append-only trigger on audit logs. Deliberately split every read predicate from its
corresponding write predicate (broader network/public read visibility must never double as
write authorization).

**Caught a real bug before calling this done**: the first pass only added `AFTER INSERT`/
`AFTER UPDATE` block predicates and forgot `BEFORE DELETE` — meaning anyone granted read access
via network-visibility sharing could have deleted a listing they didn't own. Found this by
actually writing an adversarial test script (`Data/Security/rls_test.sql`) rather than trusting
the SQL by inspection: seeded two orgs/users, tried to read/update/delete across the tenant
boundary, and the delete-without-block gap showed up immediately as "0 rows... wait, that
should have errored." Rolled back the migration, added `BEFORE DELETE` block predicates for
Listings/Demands/both Contact tables (not needed for the Collaboration tables — their read and
write predicates are already identical, so the filter predicate alone already restricts
delete), regenerated the migration, reapplied, and reran the full test — all 7 scenarios now
pass, including the specific delete-after-read-grant case that exposed the bug.

Seeded RBAC (4 roles × 17 permissions from spec §7, with a documented default grant matrix) and
feature flags (all 13 from spec §15, off). Reference data seeding was deliberately restrictive:
only seeded what the spec itself explicitly enumerates as concrete values (9 land area units,
4 demand purposes, Nepal's 7 provinces, NPR currency) — left property types, amenities,
districts/municipalities/wards/localities empty since the spec marks those admin-configurable
without giving an exhaustive list, and inventing one would be exactly the kind of fabricated
content spec §22 prohibits. Also deliberately did not seed a SuperAdmin user account (needs a
real password via a proper flow — that's Stage 4, not a hardcoded credential).

**Verified**: clean build after every change; both migrations applied to a real database; the
RLS test script's all 7 scenarios pass (owner access, outsider denial, hostile update/delete
blocked, read-without-write after a visibility grant, anonymous denial then correct anonymous
access once genuinely public, audit-log append-only enforcement); seeded data spot-checked via
direct SQL.

**Known gaps, documented rather than silently skipped**: no RLS yet on `ListingDocument`/
`ListingMedia` (public/private media split) or general `Profile`/`MemberEntity` PII protection
— reasonable Stage 13 (security hardening) follow-up. Contact disclosure only resolves to a
specific listing/demand when the collaboration originated from a match. The
`app.profile_id`/`app.is_system_admin` session context the predicates depend on isn't wired
into the request pipeline yet — that needs Stage 4's JWT auth middleware; until then every
predicate fails closed, which is correct, not a bypass.

## Stage 4 — Authentication + Member Organizations (✅ complete, same session)

Connected Stage 3's RLS to real requests: `SessionContextConnectionInterceptor` (an EF Core
`DbConnectionInterceptor`) reads `HttpContext.User` — populated by JWT auth middleware before
any controller or EF query runs — and calls `sp_set_session_context` the moment a connection
opens, on every request. Proved this actually works (not just by reading the code): added a
temporary debug endpoint that queried `SESSION_CONTEXT` back and returned it in the response —
logging in as the bootstrapped SuperAdmin and as a freshly-invited MemberAdmin each showed
exactly the right profile ID and admin flag reaching SQL Server, and an anonymous request showed
neither. Deleted the debug endpoint once confirmed.

Built real login/refresh/logout/change-password/forgot-password/reset-password
(`Services/Auth/AuthService.cs`) — short-lived (15 min) JWT access tokens, opaque refresh tokens
hashed at rest and rotated on every use, single-use hashed password-reset tokens.
`ActiveProfileMiddleware` re-checks `Profile.IsActive` against the database on every
authenticated request (not just at login) so a suspension revokes access immediately even for a
token that hasn't expired yet — the spec's explicit requirement (§2.2). Verified directly:
suspended a logged-in user mid-session with their token still valid, and the very next request
with that same token was rejected.

JWT carries the caller's permission slugs (computed fresh from role assignments at login/refresh
— never a bare role-name check, spec §7) plus an `is_system_admin` flag matching the RLS
predicates' own bypass semantics exactly. A `RequirePermissionAttribute` filter gates admin
endpoints, documented as a UX/API convenience only since the database RLS is the real authority
either way (spec §2.5).

Implemented Flow A end-to-end (spec §2.4): public membership application (gated by the
`membership_application_enabled` feature flag) → admin approve (creates the `MemberEntity` +
sends — well, logs, no email provider exists yet — a `MemberAdmin` invitation) → invitation
accept (handles both a brand-new profile setting its first password and an existing profile
joining a second org) → login as the new member. Ran the entire chain for real via curl,
including a refresh-token rotation, a rejected reuse of the rotated-out token, and a 403 when the
new MemberAdmin tried an admin-only action.

Solved the bootstrapping problem (a permission system starts with nobody in it, so nobody could
call the admin endpoints needed to create the first real admin): `DatabaseSeeder.SeedSuperAdminAsync`
runs only while zero System-scope role assignments exist anywhere, and only if
`REAK_BOOTSTRAP_ADMIN_EMAIL`/`REAK_BOOTSTRAP_ADMIN_PASSWORD` are supplied via environment
variables/user-secrets — never a hardcoded credential, and permanently a no-op once a real
SuperAdmin exists. `REAK_JWT_KEY` follows the same never-committed pattern; the API fails fast
at startup if it's missing rather than silently signing tokens with a default key.

No email provider is wired up yet — `LoggingEmailSender` logs invitation/reset emails instead of
sending them, clearly commented as a pre-production swap-in point rather than a fabricated "sent"
claim.

Frontend: replaced the Stage 2 "not yet available" placeholders for login, forgot/reset
password, and membership application with real forms (Next.js Server Actions, httpOnly session
cookies — the browser never touches the JWT or refresh token directly). Added `/invite/[token]`
(not one of the spec's original 20 public routes — necessary once invitations are real) and a
minimal `/portal` placeholder that proves the round trip (reads the session, calls `/api/auth/me`,
shows who's signed in) without building anything Stage 5 owns.

**Verified**: `dotnet build` clean; all auth/RBAC/Flow-A logic exercised for real via curl
end-to-end (not just unit-level); `rls_test.sql`'s 7 scenarios rerun after the new migration —
still pass, no regression; `npm run build`/`npm run lint` clean; unauthenticated `/portal`
redirects to `/login`; a real invitation rendered correctly on `/invite/[token]` fetched from the
live API. All smoke-test data (test org, test profile, test invitations) cleaned out of the local
dev database afterward.

**Known gaps for later stages**: no RLS yet on `RefreshTokens`/`PasswordResetTokens`/`Profiles`/
`MemberEntities`/`Invitations`/`MembershipApplications` (consistent with the Stage 3
`Profile`/`MemberEntity` gap already noted — Stage 13 territory, not a live risk today since only
the API writes these and every mutation already checks ownership in application code). No silent
browser-side access-token refresh (Next's own docs say Proxy isn't meant for full session
management, and Server Components can't set cookies mid-render) — a 15-minute-old session just
means signing in again until Stage 5 builds real persistence. No CORS setup — unneeded since only
the Next.js server calls REAK.Api, never the browser directly.
