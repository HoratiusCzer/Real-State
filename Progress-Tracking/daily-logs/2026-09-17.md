# Daily Log — 2026-09-17

## Stage 8 — Matching Engine (✅ complete)

Full write-up in `DEVELOPMENT_PLAN.md`'s Stage 8 section — summary here.

Built the scoring core (`MatchingEngine`, spec §12): nine criteria (Location, Price/budget,
Area, PropertyType, Purpose, Bedrooms, Bathrooms, Amenities, Furnishing), every weight/
tolerance/required-flag pulled from the currently *Published* `MatchRuleSet`'s rows, never
hardcoded. A criterion missing data on either side is excluded from the score's numerator and
denominator rather than penalized. No published rule set → the engine and the API both say
"Matching is not yet configured by REAK" (spec's exact wording), never a placeholder score-0
match. `MatchRuleSetsController` gives admins the minimal CRUD to actually author and publish
rule sets — same "unblock the feature now, defer the full manage UI to Stage 11" pattern used
throughout this project. Recompute wired into `ListingService`/`DemandService`'s submit/
approve/update/replace-set methods, matching spec Flow C ("a listing or demand is created or
updated"); a member's own shortlist/dismiss/reopen decision survives recomputation untouched.

**Found and fixed two genuine, non-obvious bugs** by actually running the thing against two
real organizations rather than trusting the code on read-through:

1. The matching engine shares its `DbContext`/connection with the triggering HTTP request, so
   Stage 4's RLS interceptor had already stamped that connection with the *triggering user's*
   identity — meaning "find every Approved listing to match against this demand" silently
   RLS-filtered down to only what that one user could see, which is backwards for a
   system-level cross-organization computation. First attempted fix (a single ad hoc
   `sp_set_session_context` call before the engine's queries) didn't work, because EF Core
   opens/closes its connection around each *individual* operation rather than once per request
   — the interceptor re-stamped the ambient caller's identity back before the very next query
   ran. Real fix: `SessionContextOverride`, a scoped flag the interceptor checks on every
   connection-open, set for the duration of the whole recompute and reset in a `finally` —
   spec §20's "security-sensitive database function" pattern, implemented explicitly.
2. The exact same JOIN-collapse issue hit `MatchesController` and `DashboardController`'s
   `PotentialMatchesCount`: any query reading `m.Listing.MemberEntityId` and
   `m.Demand.MemberEntityId` in one LINQ expression joins to both RLS-protected tables, and
   RLS's filter predicate applies to a JOIN target regardless of which columns are projected —
   so a listing owner who doesn't also own the matched demand (the normal case) had their own
   match silently hidden. Same fix, same pattern: elevate to read, authorize in C#.

Caught the first because a match that should obviously have existed just never appeared —
traced it by hand instead of assuming a tolerance/constraint bug. Caught the second immediately
after, on the hypothesis that the identical JOIN shape would have the identical problem — it
did, confirmed via a real cross-org 403 test before the fix and a real cross-org 200 (leaking
the full match to an uninvolved third org) that motivated it.

None of the matching tables have RLS (spec never asked for it, and a Match reveals a
compatibility relationship between two specific orgs' private data — arguably more sensitive
than either side alone), so `MatchesController` does its own explicit ownership check
everywhere, deliberately more conservative than Listing/Demand RLS itself.

Frontend: `/portal/matches` (browse, verbatim "not configured" state) and `/portal/matches/:id`
(full explanation with per-criterion icons/detail text, plus all five spec §12.1 actions —
shortlist, dismiss, reopen, request collaboration, report incorrect data). Request-collaboration
is recorded as an auditable action but does not create a real `CollaborationRequest` yet —
that's Stage 9, and the response says so rather than silently no-opping.

**Verified end-to-end**, methodically, after both bugs were fixed: a 100%-match pair with a
real rule set; pushing price 4.55% over budget → Partial, score dropped to 85 (hand-verified
weighted-average arithmetic); pushing it 82% over → Fail without exclusion (not marked
required), score 70; changing property type outside the demand's accepted list → the pair
correctly excluded entirely (Match row deleted — 404 on detail, 0 in search); a third,
uninvolved org got 403 on both match detail and record-action; a shortlisted match survived a
subsequent listing edit without reverting to New. Reran `rls_test.sql` after all the
interceptor changes — still 7/7, no regression. `dotnet build`/`npm run build`/`lint` clean. All
test fixtures cleaned from the dev database afterward.

**Known gaps carried forward**: rule sets are API-only to author today (real admin UI is Stage
11); recompute is synchronous and scoped one-sided per write (fine at current scale — a
background job queue is the right answer only once that stops being true, not before).

## Stage 9 — Collaboration (✅ complete)

Full write-up in `DEVELOPMENT_PLAN.md`'s Stage 9 section — summary here.

Built the request lifecycle (`CollaborationRequestService`: from-match or standalone to-org,
accept/decline/cancel) and the workspace-scoped surface (`CollaborationWorkspaceService`:
messages, notes, tasks, viewings, files, activity log, contact disclosures), wired into two new
controllers and `MatchesController`'s `RequestCollaboration` action (which previously just
logged a placeholder note).

Proactively identified — *before* writing or testing any code, applying the exact lesson learned
from Stage 8's bugs — the RLS bootstrap chicken-and-egg problem for creating a
`CollaborationWorkspace`: its shared participant predicate blocks inserting the very first
participant rows, since the caller isn't a participant of a workspace that doesn't exist yet
until those rows land. Solved with the same `SessionContextOverride` elevation Stage 8 built,
scoped to just that one bootstrap `SaveChangesAsync`.

Confirmed the reason this stage exists at all works: `ListingsController`/`DemandsController`'s
`.../contact` endpoints (Stage 6/7) already checked for an unrevoked `CollaborationContactDisclosure`
— granting one through the new `POST .../contact-disclosures` endpoint required zero changes to
either controller, and revoking it re-hid the contact live. Verified with two real orgs (Kathmandu
Prime / Pokhara Lakeside) and their existing 100%-match fixture: full request → accept → workspace
flow; a same-org, non-participant profile correctly got 404 on the workspace and 403 attempting to
post into it (collaboration participation is per-profile, not per-organization — confirmed
deliberately, not assumed); `ListingContact` disclosure grant/revoke correctly toggled the Stage 6
contact endpoint's response live; granting `Phone`/`Email` (enum values with no RLS predicate
backing them) correctly refused rather than silently no-opping; messages/notes/tasks/viewings/
files all worked bidirectionally and stayed invisible to the non-participant. Reran `rls_test.sql`
— still 7/7, no regression (no RLS SQL touched this stage). `dotnet build`/`npm run build`/`lint`
all clean.

Frontend: `/portal/collaborations` (list with inline accept/decline/cancel) and
`/portal/collaborations/:id` (full workspace UI), plus a standalone "Request collaboration"
affordance on `/portal/members/:id`. **Not visually verified in a browser** — the Chrome
extension wasn't connected in this environment (same gap since Stage 2); backend was verified
via real HTTP calls against every endpoint instead.

Reset passwords for the `kathmandu-prime@example.test`, `pokhara-lakeside@example.test`, and
`kathmandu-staff@example.test` test accounts (created in an earlier session) via the real
forgot-password/reset-password flow to run these tests — all three are now `TestPass123!`, and
the fixture match/listing/demand/collaboration data from testing was left in place rather than
cleaned up, so this can be visually checked in a browser directly.

## Stage 10 — Notifications (✅ complete)

Full write-up in `DEVELOPMENT_PLAN.md`'s Stage 10 section — summary here.

The `Notification` entity, `NotificationsController` (list/mark-read/mark-all-read), and even the
frontend `/portal/notifications` page already existed from earlier scaffolding — nothing had ever
actually created a row. Built `INotificationService`/`NotificationService` (parallel to
`IEmailSender`) and wired it into eight of spec §14's nine triggers: new matches (only genuinely
new ones, not score-refresh recomputes), collaboration request/accept/decline, workspace messages
(notifying every other participant), listing approval/rejection, invitation acceptance (notifying
the inviter — the invitee has no profile to notify until that exact moment), password change/reset,
and expiry.

Expiry needed a new `ExpiryScanService` background job — the first genuine background job in this
codebase — since there's no HTTP request to hook a controller action onto. It elevates via
`SessionContextOverride` (third use of that Stage 8 pattern now: MatchingEngine, collaboration
workspace bootstrap, and now this) since a background job has no ambient identity at all for the
RLS interceptor to read. Found and fixed a real, if narrow, schema gap while building this:
`DemandStatus` had no `Expired` value despite `Demand` already having an `ExpiresAt` column
(`ListingStatus.Expired` already existed but was likewise never used) — added it rather than
overloading `Archived` for a different state.

Deliberately left association notices unwired: there's no publish mechanism for `Notice` yet (CMS
management is Stage 11), so there's no real event to hook a notification to — same "don't fabricate"
call as Stage 8's Furnishing criterion.

Verified end-to-end with the same real organizations from Stage 9: message notifications correctly
excluded the sender; the full collaboration request/accept/decline cycle produced correct
notifications with working deep links; temporarily enabling `property_moderation_required` (off by
default in this dev DB) let a real listing rejection and approval both be tested, then the flag was
restored; an invitation created and accepted notified the inviter; a password reset notified the
account; backdating the demo listing/demand's `ExpiresAt` and restarting the API triggered the
scan, correctly expiring both, notifying both orgs, and dropping the pair out of the live match
view — both were then restored to their prior Approved/Active state since they're the main demo
fixture used across several stages now. `unread-count` tracked correctly throughout, including
zeroing on mark-all-read. Reran `rls_test.sql` twice — still 7/7. `dotnet build`/`npm run build`/
`lint` all clean.

Frontend needed only two small additions since the notifications page already existed: a clickable
title when a notification carries a `linkUrl`, and an unread-count badge on the sidebar's
Notifications item. **Not visually verified in a browser** — the Chrome extension still isn't
connected in this environment; verification was backend-authoritative (real HTTP calls) plus clean
builds, same caveat as Stage 9.
