# Daily Log — 2026-09-18

## Stage 14 — Performance + Accessibility + Responsive QA (✅ complete)

Full write-up in `DEVELOPMENT_PLAN.md`'s Stage 14 section — summary here.

Chrome browser automation became available for the first time this session. Every prior stage's
"browser QA" was actually curl/HTTP-level verification — this is the first stage checked against
an actually-rendered page, and it paid off immediately.

**Real, previously-shipped bug found and fixed**: `IFileStorage.GetPublicUrl()` returns a relative
`/media/<file>` path with no opinion on origin. Rendered as `<img src>`, it resolved against the
Next.js app's own origin (3000) instead of the API's (5080) — every listing photo has 404'd since
Stage 6. Fixed with a `next.config.ts` `rewrites()` entry proxying `/media/:path*` to
`REAK_API_URL`, the same server-side-proxy pattern every other cross-origin call in this app uses.

**Converted image rendering to `next/image`** (property cards, property detail pages, wizard
upload previews) with `fill`/`sizes`/`object-cover`. While verifying this in the browser, hit a
second, genuinely confusing issue: the browser showed a broken-image icon for the one real test
listing photo, despite curl/`fetch()` against the same URL both returning clean `200 image/jpeg`.
Traced it by fetching the raw bytes in-page: the file was a 19-byte stub (`ff d8 ff e0` + the
literal text "qa-test-phot...") — leftover fixture data from an earlier stage's curl upload test,
never a real image. HTTP-level checks don't validate image content, so nothing before this stage
could have caught it; a real browser's decoder correctly refused to render it. Not a code bug.
Swapped in a real 1x1 JPEG to confirm the `next/image` + rewrite pipeline actually works — it does.
Bonus finding: this Next.js version's dev image-optimizer cache lives at
`.next/dev/cache/images`, not the legacy `.next/cache/images` path; clearing the wrong directory
left the optimizer serving the stale broken result.

**Responsive fix**: `PortalSidebar`/`AdminSidebar` had zero mobile behavior (spec §23's "shrunken
desktop" anti-pattern, applied to nav instead of a table). Both now collapse below `md` into the
same disclosure-button pattern `SiteHeader`'s mobile nav uses. Hit and fixed a
`react-hooks/set-state-in-effect` lint error along the way, using React's documented
compare-during-render pattern instead of a `useEffect`. `resize_window` did not actually change
the captured viewport in this environment (3 attempts) — mobile-breakpoint pixel verification
wasn't possible; verified instead by reading the rendered DOM/CSS for correct `md:hidden`/
`hidden md:block` classes.

**Also shipped this stage**: `loading.tsx`/`error.tsx` for all three route groups (6 new files,
`error.tsx`'s reset prop is `retry` in this Next.js version, not `reset`); a real `sitemap.ts`
pulling live published content (20 URLs, was 14 static); `generateMetadata`/canonical/OG on every
public page; opt-in `revalidate: 3600` caching for reference/taxonomy data only; two missing
`aria-label`s on icon-only buttons; a dead download link fixed via a new proxy route.

**Verified live in an actual browser**: logged in as a real member, dashboard/property
list/property detail/navigation all render correctly, `/media` rewrite returns 200, the
broken-image investigation resolved end-to-end with a visual before/after. `npm run lint` and
`npm run build` both clean (65 routes). No RLS change this stage.
