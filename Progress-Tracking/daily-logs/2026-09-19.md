# Daily Log — 2026-09-19

## Post-Stage-16: user acceptance testing found a real duplicate-data bug

With all 16 stages complete, the user started their own manual testing against the
now-running API/frontend. First thing checked — `GET /api/reference/property-types` — turned up
a real bug within minutes: "Apartment" and "Land" each appeared twice with different IDs.

**Root cause**: none of `ReferenceDataController`'s 7 taxonomy `POST` endpoints (property types,
subtypes, purposes, amenities, districts, municipalities, wards, localities) checked for an
existing row with the same name before inserting, and none of the underlying tables had a
uniqueness constraint either — so calling create twice with the same name silently produced two
rows. Checking every reference table found the same pattern had already happened, presumably
during earlier-stage manual testing before this build's current daily-log history began:
`PropertyTypes` (Apartment ×2, Land ×2), `Purposes` (Sale ×2), `Districts` (Kathmandu ×2),
`Municipalities` (Kathmandu Metropolitan City ×2, with its own duplicate Ward).

**Fix**: added an existence check to all 7 create endpoints, scoped to the right parent where one
exists (a district's uniqueness is scoped to its province, a municipality's to its district, a
ward number's to its municipality) or global for the flat taxonomies (property types, purposes,
amenities). `dotnet build` clean, 0 warnings/errors.

**Cleanup**: before touching any existing data, checked every duplicate pair's actual usage
(listings, demands, subtypes, child location rows) with RLS bypassed via
`sp_set_session_context`. In every single pair, one ID was genuinely in use and the other had
zero references anywhere — safe to delete. Confirmed with the user before running the deletes
(blocked once by the harness's own irreversible-action guard, re-run after explicit approval).
Deleted the 6 orphaned rows bottom-up (ward → municipality → district → 2 property types →
purpose). Verified live: `GET /api/reference/property-types` now returns exactly one "Apartment"
and one "Land"; a fresh `POST` attempting to recreate "Land" correctly gets rejected with `400`.
`rls_test.sql` rerun clean (11/11) after the direct database writes — no regression.

Restarted the running API in place to pick up the fix (killed the process from the prior
session's background task, relaunched with the same `REAK_JWT_KEY`).

## Dedicated tenant-isolation test pass, at the user's explicit request

The user asked for a structured cross-org isolation test: two ordinary member accounts (Org A =
Kathmandu Prime Properties, Org B = Pokhara Lakeside Realty), neither a system admin, testing
read/update/delete on another org's property, access to another org's users, and (N/A for this
app — no lease/tenancy entities exist) leases/tenants. Ran each test live with exact
endpoint/method/request/response documented.

**5 of 6 applicable tests passed clean**: reading (`404`), updating (`404`, DB-verified unchanged),
and deleting (`404`, DB-verified still exists) another org's property via a deliberately
non-shared (`NetworkVisibility: OwnerOnly`) listing; updating another org's `MemberEntities`
profile (`403`). Reading another org's `MemberEntities` profile returned `200` — confirmed
intentional, not a bug: that endpoint is explicitly the spec §4.2 public member directory,
documented as such in its own code comment, exposing only public contact info.

**1 real bug found**: `GET /api/profiles`, called by the ordinary Org B `MemberAdmin` account,
returned every profile in the system across all three orgs plus both system admins — email, full
name, last login, org memberships, and role assignments included. Root cause: gated only by
`RequirePermission("members.read")`, a slug shared between System-scoped roles (who should see
everyone) and the Organization-scoped `MemberAdmin` role (who shouldn't) — unlike
`MemberEntitiesController.Update`, which already explicitly checks `IsSystemAdmin` before a
cross-org action, this endpoint trusted the permission slug alone. Per the user's explicit
instruction, showed them the bug and a proposed fix before touching any code; fixed on their
go-ahead by scoping the query to the caller's own organization(s) unless they're a system admin.
Verified live: Org B now sees only its own single user; a system admin's view is unchanged (still
all 7 profiles). Committed as `b11e52d`.

This is a genuine finding Stage 15's regression pass did not catch — that pass exercised
`GET /api/profiles` only as a system admin (the natural account for an admin-only-looking
endpoint), never as an ordinary member, which is exactly the gap here.
