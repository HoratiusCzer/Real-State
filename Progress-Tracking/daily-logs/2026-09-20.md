## Removed AssociationAdmin, collapsed into SuperAdmin (attempted, reverted, redone with sign-off)

Came out of the user walking a client through a live demo and asking, mid-walkthrough, whether

accounts could do identical things in the Admin Portal. Verified against the real permission

branched on which of the two a caller held.

**Scope check before touching anything**: grepped the whole codebase for `AssociationAdmin` —
found it in exactly three places: a doc comment in `MemberEntitiesController.cs` (no functional
role-name check), the seeder's role list, and one migration-file comment (left alone — migration
history isn't retroactively edited). No code anywhere does a functional `Role.Name ==
"AssociationAdmin"` branch, unlike `"MemberAdmin"` which genuinely is checked by name elsewhere —
a safe, contained removal with zero logic-branch impact.

**First pass**: implemented the removal (seeder + comment update), reassigned the one profile
(`assoc-admin@example.test`) and the one historical invitation record that referenced the role
over to `SuperAdmin` (checked both reference points before touching anything, preserved rather
than deleted), removed the role and its grants. Verified live, committed (`80fd735`), pushed.

**User asked for a revert** immediately after ("revert the channges i dont want to push this") —
already on the shared remote by then, so undone via `git revert` (two new commits) rather than
rewriting pushed history. The revert only undoes tracked *files*; it doesn't touch a live
database that was directly modified via SQL, so the `AssociationAdmin` role, its permission
grants, and both reassignments were manually re-created/restored first, then the code revert
committed and pushed. Verified restored to the original 4-role state before moving on.

**User then re-sent the same instruction with explicit sign-off and verification steps spelled
out** — redone identically (same two files, same shape of diff), this time showing `git status`/
`git diff` before committing as asked. Verified: exactly 3 roles exist; `SuperAdmin` still has
all 18 permissions; `assoc-admin@example.test` holds `SuperAdmin`, logs in, `isSystemAdmin: true`,
full admin access confirmed live (`audit-logs`/`reports/summary`/`feature-flags` all `200`).
`rls_test.sql` rerun clean (11/11) both times. Committed as `f8271bc`, pushed.

Net effect of today's back-and-forth: `AssociationAdmin` is gone, `SuperAdmin` is the sole
system-scoped role, and the full history (add → revert → redo) is preserved honestly in git
rather than squashed away, since the user's own decision-making process — confirm, reconsider,
confirm again — is itself worth keeping a record of.

## Full data reset to a clean slate for a real end-to-end walkthrough

User wants to run the entire flow themselves from scratch (membership application → invitation →
listing → demand → match → collaboration) without wading through this session's accumulated test
data. Asked for everything wiped except: `dev-admin@reak.local` (sole surviving profile), the RBAC
structure (Roles/Permissions/RolePermissions), all reference/taxonomy data (property types,
amenities, purposes, area units, currencies, Nepal provinces/districts/municipalities/wards/
localities), and the 13 `FeatureFlags` definitions — with every flag's value reset to its seeded
default (`false`), not whatever testing left them at.

**Before touching anything**: produced a full inventory (table + row count) of everything to be
deleted, confirmed the four preserved categories and their counts, and mapped every FK in the
schema (`sys.foreign_keys`) to fix a child-before-parent deletion order — several are `NO_ACTION`,
same pattern as the earlier SuperAdmin cleanup. Got explicit sign-off before running anything.

**Exported `AuditLogs` first** (251 rows, `Progress-Tracking/exports/audit-logs-2026-09-20.json`,
not committed to git — a local backup, not a code change) — recommended this over just trusting the
daily logs, since the log entries are prose written after the fact, not the original structured,
timestamped, actor-attributed record.

**Two real problems hit during execution, both fixed**:
1. `AuditLogs` has an append-only trigger (`trg_AuditLogs_PreventModification`) enforcing the
   spec's append-only requirement at runtime — blocked the delete outright. Disabled it for that
   one `DELETE` (inside the same transaction, re-enabled before commit), since this is an explicit
   user-confirmed one-time dev-data reset, not a runtime code path.
2. **More serious**: `Demands`, `PropertyListings`, `DemandContacts`, `ListingContacts`, and the
   `Collaboration*` tables are all protected by native RLS security policies keyed off
   `SESSION_CONTEXT('app.is_system_admin')`/`SESSION_CONTEXT('app.profile_id')` (set by the app's
   `SessionContextConnectionInterceptor` on every real request). A raw `sqlcmd`/`Invoke-Sqlcmd`
   connection sets neither, so RLS silently filtered those tables to 0 visible rows — the `DELETE`
   statements "succeeded" but deleted nothing, and `SELECT COUNT(*)` on the same connection also
   showed 0, masking the problem until the later `MemberEntities`/`Profiles` deletes hit real FK
   conflicts from rows that were still physically there. Caught it by comparing `SELECT COUNT(*)`
   (RLS-filtered) against `sys.partitions` row counts (physical, bypasses RLS) — found the
   mismatch, then re-ran the blocked deletes after `EXEC sp_set_session_context
   @key=N'app.is_system_admin', @value=1` on that connection, which the predicate functions
   (`fn_DemandWritePredicate`/`fn_ListingWritePredicate`/etc.) explicitly allow as a bypass.

**Final state, verified via `sys.partitions` (physical counts, not RLS-filtered)**: all 39
in-scope tables at 0 rows. `Profiles`/`ProfileRoleAssignments` at 1 row each (`dev-admin@reak.local`
/ `SuperAdmin`). `FeatureFlags` still 13 rows, all `IsEnabled = 0`, `UpdatedByProfileId` nulled out
on the 5 that had pointed at a now-deleted profile. Reference/taxonomy tables and RBAC tables
untouched (`Roles` 3, `Permissions` 18, `RolePermissions` 36, plus all the geo/property/purpose/
currency/area-unit tables at their original seeded counts).

**Verified live**: `dev-admin@reak.local` still logs in, `is_system_admin: true`, full 18-permission
token, real `200`s on `/api/audit-logs` and `/api/reports/summary`. `rls_test.sql` rerun clean — all
7 steps behaved as expected (owner sees own listing, cross-org read/write correctly blocked, public
visibility toggle works, append-only trigger still blocks audit log tampering) — no regression from
the trigger disable/re-enable.

**No code changed** — `git status` came back with only the untracked `Progress-Tracking/exports/`
file; nothing to commit on the code side. This log entry plus the JSON export are the only
artifacts.

**For the E2E test**: only 3 of the 13 flags gate anything real in the current codebase (checked
