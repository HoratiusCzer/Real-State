# Daily Log — 2026-09-20

## Removed AssociationAdmin, collapsed into SuperAdmin

Came out of the user walking a client through a live demo and asking, mid-walkthrough, whether
`SuperAdmin` and `AssociationAdmin` were actually the same thing — they'd noticed both admin
accounts could do identical things in the Admin Portal. Verified against the real permission grants
(not assumed): both roles held the exact same 18 permission slugs, no code anywhere branched on
which of the two a caller held. Confirmed, then removed on request.

**Scope check before touching anything**: grepped the whole codebase for `AssociationAdmin` —
found it in exactly three places: a doc comment in `MemberEntitiesController.cs` (no functional
role-name check), the seeder's role list, and one migration-file comment (left alone — migration
history isn't retroactively edited). No code anywhere does a functional `Role.Name ==
"AssociationAdmin"` branch, unlike `"MemberAdmin"` which genuinely is checked by name elsewhere —
meaning this was a safe, contained removal with zero logic-branch impact.

**Seeder is additive-only** (checked before assuming): it only inserts a role if missing, never
deletes one no longer in its list. Removing `AssociationAdmin` from `DatabaseSeeder.cs` prevents it
from ever being recreated on a fresh install, but doesn't touch this already-seeded dev database —
that needed a direct, separate cleanup.

**Live database cleanup**: checked every reference to the role first (`ProfileRoleAssignments`: 1
row — `assoc-admin@example.test`'s own assignment; `Invitations`: 1 row — a historical, already-
accepted invitation record) before deleting anything. Reassigned both to `SuperAdmin` rather than
deleting them, preserving history instead of losing data, then removed the role's permission
grants and the role row itself.

**Verified live**: `assoc-admin@example.test` still logs in, `isSystemAdmin: true`, all 18
permissions intact, every admin endpoint (`audit-logs`, `reports/summary`, `feature-flags`) still
`200`s — reassigning the role changed nothing about what the account can actually do, only removed
the redundant second name. `GET /api/reference/roles` now lists exactly 3 roles (`SuperAdmin`,
`MemberAdmin`, `MemberStaff`). Build clean, `rls_test.sql` rerun clean (11/11).

Committed as `80fd735` and pushed.

## Other things surfaced during the same walkthrough, not yet acted on

- **Member orgs can't self-service invite their own staff.** Checked live: `POST /api/invitations`
  requires `members.create`, which only `SuperAdmin` holds — a `MemberAdmin` (e.g. Softsaro's own
  admin) cannot invite colleagues into their own organization; every single invitation for every
  org has to go through REAK's central admin. Flagged to the user as a real product decision for
  the client to make (intentional centralized control, vs. a real gap worth building self-service
  invites for) — not yet decided, nothing changed.
- **Org suspension doesn't cut off member access.** Reconfirmed live (user tested it themselves):
  suspending Softsaro PTV LTD via `/admin/member-organizations` only hides it from the directory;
  its staff can still log in and use the system fully. This is `MemberEntitiesController.Suspend`'s
  own documented, deliberate design from an earlier stage — but flagged to the user as worth
  reconsidering for a real association (does "suspend a member" mean "hide from directory" or
  "cut off access"?). Not yet decided, nothing changed.
- **A bulk Excel-import feature was scoped, partially implemented, then explicitly reverted** at
  the user's request mid-implementation ("stop this, revert this, i want to stop now"). Reverted
  cleanly: three new files deleted, three modified files restored via `git checkout --`, confirmed
  clean `git status` and a successful build afterward. Nothing from that attempt remains in the
  codebase. If this comes back later, the design work (ClosedXML, name-based reference-data
  resolution reusing `CreateListingRequest`'s existing validation, per-row partial-success
  reporting, a downloadable template) doesn't need to be redone from scratch — it's preserved in
  this session's transcript even though no code survived.
